# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Commands

Windows with Git Bash, Gradle wrapper: `./gradlew.bat` (PowerShell: `.\gradlew.bat`). Requires JDK 17 and the Android SDK for platform 37 (compileSdk 37, minSdk 26).

- Build debug APK: `./gradlew.bat assembleDebug` → `app/build/outputs/apk/debug/app-debug.apk`
- Install on the running emulator/device: `./gradlew.bat :app:installDebug`
- All unit tests: `./gradlew.bat testDebugUnitTest`
- Unit tests of one module: `./gradlew.bat :untis:test` or `:app:testDebugUnitTest`
- Single test class: `./gradlew.bat :untis:test --tests "com.bdersolutions.daybreak.untis.TotpTest"`
- Windows desktop app (`:desktop`, Compose Multiplatform): `./gradlew.bat :desktop:run` to start it, `:desktop:windowsInstaller` for the one-click installer `Daybreak-<version>-setup.exe` (`desktop/build/installer`; needs Inno Setup 6: `winget install JRSoftware.InnoSetup`, or set `INNO_SETUP_COMPILER` to `ISCC.exe`), `:desktop:portableZip` for the ZIP (`desktop/build/distributions`). Pass `-Pdaybreak.versionName=1.2.3` to set the version. `:desktop:packageMsi` still works but the MSI is no longer released. The GitHub workflow `.github/workflows/windows.yml` builds the installer and the ZIP on `feat/windows-port`; `release-windows.yml` attaches them to a release.
- Single method: append `.methodName` to the `--tests` class name (same pattern).
- Lint: `./gradlew.bat :app:lintDebug` currently **fails** with 30 errors and about 130 warnings (none from the widget code) (report: `app/build/reports/lint-results-debug.html`). Do not pass `--offline` to lint: the lint tool artifact is not cached and the build breaks.
- Other Gradle runs work with `--offline` once dependencies are cached.

The only instrumented test is `PinchToZoomTest` (`app/src/androidTest`). **Do not run `connectedDebugAndroidTest` on an emulator that is signed in**: it uninstalls the app afterwards and the login is gone. Install the APKs (`:app:installDebug`, then `adb install -r` the output of `:app:assembleDebugAndroidTest`) and run `adb shell am instrument -w -e class com.bdersolutions.daybreak.ui.timetable.PinchToZoomTest com.bdersolutions.daybreak.test/androidx.test.runner.AndroidJUnitRunner`. Espresso must be 3.7+ on API 37 (3.5 calls a removed `InputManager.getInstance`).

Debugging a device: debug builds allow `adb shell run-as com.bdersolutions.daybreak cat files/raw_api_responses.json` (raw WebUntis responses) and `cat files/timetable_cache.json`. The same raw log is shown in Settings → Debug log, which is hidden until the theme option "System" is tapped ten times.

## Architecture

Two Gradle modules. `:untis` is an Android library holding the WebUntis client; `:app` is the Compose application. The `:app` module never sees JSON-RPC payloads, URLs, or TOTP.

**`:untis`** — `UntisApi` is the facade. `JsonRpcClient` posts to the 2017 mobile JSON-RPC endpoints (`getTimetable2017`, `getStudentAbsences2017`, `getExams2017`, …). Login uses a TOTP secret from the Untis QR code, or a password once to fetch the mobile secret (`loginWithPassword`). Parsers (`TimetableParser`, `SchoolDataParser`, `ExamParser`) are deliberately tolerant: they accept several field aliases, skip malformed entries, and produce normalized models (`UntisLesson`, `UntisAbsence`, `UntisExam`, `UntisDirectory`). `RawResponseSink` is how responses reach the debug log. Passwords and the mobile secret are never recorded (`recordRaw = false`).

**`:app` wiring** — `DaybreakApplication` owns `AppContainer`, a hand-written service locator that builds the repositories, stores, and schedulers. `MainActivity` applies the stored language through `AppCompatDelegate` and calls `DaybreakApp`, which wraps everything in `DaybreakTheme`. `DaybreakRoot` (in `ui/DaybreakRoot.kt`) switches between login and `LoggedInContent` by session. The logged-in area has three bottom tabs (Timetable, Absences, More). The More tab (`SettingsScreen`, string `nav_settings`) groups its rows under three labels: My profile (account, messages), Settings (appearance, timetable, lesson colours, language, sync, notifications) and Other (debug, updates, about). Each row opens its own screen. The screens are the `SettingsPage` enum (`ui/settings/SettingsPages.kt`: appearance, timetable, lesson colours, language, sync, notifications, about); `LoggedInContent` keeps the open page (`Destination`: a settings page, Upcoming, Account, Messages or Debug) in one saveable state and shows it through `PushHost` (`ui/components/PushNavigation.kt`). There is no navigation library. **Every full-screen page goes through `PushHost`**: an iOS-style push (page slides in from the right, the screen underneath shifts left by 28 % and dims, no-bounce spring) whose back is a `PredictiveBackHandler`, so the system back swipe drags the page and can be cancelled. Hosts nest (Messages pushes the opened message). The spring starts two frames late on purpose: the first frame of a new page is long, and a spring started with it arrived almost in place. Do not put an elevation shadow on the moving page (it dropped most frames); the edge shadow is a gradient. Quick pickers and details (lesson details, search, timetable picker, writing a message, absence categories) stay `ModalBottomSheet`s.

**Windows installer** � `desktop/packaging/windows/daybreak.iss` (Inno Setup 6, chosen over Velopack and WiX Burn: it is the only one that gives a per-user, pageless, silent-capable `.exe` with a custom uninstaller without changing the app or adding a runtime/update framework; Velopack would replace the update flow, Burn still shows a wizard). The Gradle task `:desktop:windowsInstaller` runs `createDistributable` (jpackage app image with JDK 17), then `ISCC.exe` packs it into `Daybreak-<version>-setup.exe`. The setup has no pages: only a progress window with the Daybreak logo (`wizard-small-*.bmp`, made by `make-images.ps1`). It installs per user to `%LOCALAPPDATA%\Programs\Daybreak` (no admin), adds the Start menu entry and the uninstaller (HKCU), closes a running Daybreak (Restart Manager plus `taskkill`), deletes the old `app`/`runtime` folders, and starts the app at the end (also when silent, which the updater needs). `/TASKS="desktopicon"` adds a desktop shortcut that later updates keep; `/SKIPMSI=1` skips the MSI migration (for tests). The old MSI (per machine, Program Files, product code under HKLM `Uninstall` with `WindowsInstaller=1`, publisher BDER Solutions) is uninstalled with `msiexec /x` through one UAC prompt; if declined, the user install proceeds anyway. Settings and cache live in `%APPDATA%\Daybreak` and survive uninstall. The setup is not code-signed, so SmartScreen warns once. Git Bash rewrites `/SILENT`-style arguments into paths; start the setup from PowerShell when testing. In-app updates: `DesktopUpdater` downloads the setup (JSON `windows.installer`, served by `update-server` at `/v1/setup/:tag`, asset `Daybreak-x.y.z-setup.exe`), checks its SHA-256 and starts it with `/SILENT /SUPPRESSMSGBOXES /NORESTART`. Releases with only an `.msi` asset are not offered any more, so an installed MSI-era app cannot self-update; those users run the new setup once by hand (`/desktop/download`).

**Upcoming and account pages** — `MainPage` in `DaybreakRoot.kt` opens `UpcomingScreen` (homework and exams, from the checklist button in the timetable top bar) and `AccountScreen` (profile and the school notices of today, from a row at the top of Settings) over the tabs with the same slide as the settings pages. Both read through `SchoolDataRepository` (`getHomeWork2017`, `getExams2017`, `getMessagesOfDay2017`). Class services (Klassendienste) cannot be loaded in the app: the web app reads `/WebUntis/api/classreg/classservices?startDate=&endDate=&elementId=<studentId>`, which only answers a web session (cookie). With the mobile key and its `getAuthToken` token it returns the HTML page and an anonymous session (checked with five header variants), and the school may sign students in through its portal, so there may be no WebUntis password at all. The app never stores a password. The account page therefore has an "In WebUntis öffnen" button that opens `<server>/student-class-services` in the browser. If a way to get a web session ever appears, the answer is `data.classRoles[]` (id, klasse, foreName, longName, duty.label, startDate, endDate, text).

**Messages (Nachrichten)** — `MainPage.MESSAGES` opens `MessagesScreen` (inbox, sent, drafts, and a sheet with the full text) from a row in Settings. It reads the WebUntis message REST API (`/WebUntis/api/rest/view/v1/messages`, `/sent`, `/drafts`, `/{id}`). That API does not take the mobile key itself but a bearer token from `getAuthToken`, so no password is involved (`UntisApi.restGet`, `JsonRpcClient.getRest`; the token is never logged). Writing: `messages/permissions` lets a student write to teachers only, one at a time. The recipients come from `GET messages/recipients/static/persons` (groups with `displayName` and `userId`). A message is sent with `POST /WebUntis/api/rest/view/v2/messages/users` as multipart (the plain `v2/messages` is another endpoint and demands `recipientOption`) whose JSON part `request` holds `subject`, `content`, `requestConfirmation`, `recipientUserIds`, `oneDriveAttachments`, `forbidReply` (verified against the web app's own request). Do not use `recipientPersonIds`: it is a different id space and delivered a test message to the wrong teacher. The form asks for confirmation and requires the server to report exactly one recipient. Attachments are `storageAttachments` (id and name). `GET messages/{attachmentId}/attachmentstorageurl` returns a signed `downloadUrl` on the storage server plus `additionalHeaders` (server-side-encryption headers) to send with it; the file is fetched from there without the WebUntis token (`JsonRpcClient.downloadFile`, https only, 100 MB cap). That answer holds secrets, so it is never logged. `AttachmentDownloader` saves to the cache, copies to Downloads on Android 10+, and opens the file through the FileProvider. Blob attachments (`messages/{id}/attachment`) are not handled.

**Own timetable data** — `TimetableRepository` is the single source of truth for the student's own timetable. It keeps a `StateFlow` cache, persisted by `TimetableCacheStore` as `files/timetable_cache.json` (atomic write, `version` field, eight weeks at most). All fetches go through one `Mutex` in `fetchWeeks`. A week counts as fresh for 10 minutes. The same call fetches exams for the whole cached window; an exam failure is isolated and cannot hide the timetable. Subject names are merged from each fetched timetable's master data (`subjectNamesById`) and cached, so exams can be matched to lessons by subject. Absences (`getStudentAbsences2017`) are fetched and cached the same way; the timetable greys out only the part of a lesson that overlaps an absence (`absentParts` in `TimetableScreen.kt`). Holidays come from `masterData.holidays` of every timetable answer (id, name, longName, startDate, endDate; single free days are named after their date, see `UntisHoliday.hasDateName`) and are cached too (cache `version` 5, shared by the class, teacher and room views through `displayCache`). A day without lessons inside a holiday gets one synthetic block (`UntisLesson.isHoliday`, id = minus the holiday id) that fills the day range; it is never sent by the server and never cached.

**Class, teacher, and room timetables** are not cached in the repository. They are loaded on demand into `TimetableViewModel.elementWeeks`, and `displayCache` decides which cache the screen shows. `TimetableViewModel.status` is the repository status for the own timetable and a status of its own (`elementLoading`, `elementError`) for the others. A week that is not in the display cache is shown as loading (or the error), never as "free".

**Timetable layout settings** — `AppSettings.display` (`TimetableDisplay`, More → Stundenplan): `autoNextWeek` (`WeekRollover.startDate`, pure and tested: after the week's last lesson, or at a weekend, the start day is next Monday; the screen jumps there once when the cache is first known, and the Today button uses it), `dayScale`/`weekScale` (60–180 %, also set by pinching: `pinchToZoom` in `PinchToZoom.kt` listens in the Initial pass and only takes events while two fingers are down; the live zoom is `LocalTimetableZoom`, saved when the pinch ends; day blocks animate in minutes so the zoom applies without lag), `weekFitsScreen`, `concurrent` (`COMBINED`, the default, lays a week column out with one column and `combinedPriority`, so the held lesson or exam is drawn full width and the rest sit behind the "+N" chips; `SIDE_BY_SIDE` is the old two-column layout), `showCancelled`, `showFreeBands`, `weekDetail`. They reach the pages as `LocalTimetableDisplay`.

**School text** — notices and messages can be HTML. `SchoolText` (shared, tested) detects it; `schoolRichText`/`schoolPlainText` (`ui/components/RichText.kt`) turn it into styled text with links, or link plain text.

**Credentials** — `SecretVault` encrypts the mobile key with AES/GCM under a key in the Android Keystore; the ciphertext lives in the `daybreak_secure` preferences. `SessionStore.isLoggedIn()` requires both the session and a stored secret. Logout clears the key, session, cache, and raw log.

**Widget** — `widget/DaybreakWidget.kt` (Glance, `SizeMode.Exact`, lists as many rows as fit, at most 9 plus a "+N" line because Glance containers take ten children). What it shows comes from `WidgetPlanner` (`shared/.../data/schedule/WidgetPlan.kt`, pure, tested): double lessons merged with `NowAndNext.runs`, the current and next held block, and after the last lesson the next school day. Times are clock times ("bis 10:40"), never a countdown, because the widget is only redrawn at lesson boundaries (`WidgetUpdateScheduler`). Data is read **inside** `provideContent` (settings and cache flows, plus a `REFRESH_KEY` stamp in the Glance state that `WidgetUpdater` bumps): an update that reaches a live Glance session only recomposes it, so data read before `provideContent` goes stale. Colours come from the app's scheme (`daybreakColorScheme` in `Theme.kt`) and lesson colours. Settings are `AppSettings.widget` (`WidgetSettings`: theme, background opacity, second line, headline, cancelled lessons, next day after school, sync time), screen `SettingsPage.WIDGET` (`WidgetSettingsScreen`, with a pin button); `AppContainer.start()` redraws the widget when those or the colours/language change. The launcher's "Settings" on a placed widget opens that page (`APPWIDGET_CONFIGURE` on `MainActivity`, `reconfigurable|configuration_optional`). The picker preview is `res/layout/widget_preview.xml`.

**Sync** — `SyncScheduler` schedules `SyncWorker` (WorkManager) at the interval from `SettingsRepository.SYNC_INTERVALS`. The worker refreshes this week and the next, uses `LessonChangeDetector` to diff them, notifies through `LessonNotificationManager`, and updates the Glance widget through `WidgetUpdater`. Network errors become `Result.retry()`.

**Privacy and terms** — the text is in the app, not hosted: string resources `legal_*` (German and English), listed as sections in `data/legal/LegalTerms.kt` together with `LegalTerms.VERSION`. `TermsStore` (`daybreak_terms` preferences, kept apart from the session so logout does not reset it, and left out of backups) records the accepted version. `DaybreakApp` shows `TermsGateScreen` instead of `DaybreakRoot` until `TermsAcceptance.covers(accepted)`, so no login, sync prompt or update check runs before acceptance; declining closes the app. An update asks again only when `VERSION` went up. **When you change the meaning of the section texts, raise `LegalTerms.VERSION`**; `LegalTermsVersionTest` hashes the section strings and fails otherwise (the failure message gives the hash to record). The same text is readable afterwards under More → Privacy and terms (`SettingsPage.LEGAL`). The contact section names the GitHub project; the developer must keep the text accurate when the app starts sending or storing something new. Background workers (sync, update check) are not gated.

**Updates** — `update-server/` is a small Fastify service (own `package.json`, tests with `npm test`, deployed on Coolify with base directory `/update-server`). It mirrors the APK and changelog of the latest GitHub release; the app never talks to GitHub. `.github/workflows/release.yml` builds and signs the APK when a release is published. In the app, `data/update/` holds the client: `UpdateManager` (check, download with SHA-256 check, install through `PackageInstaller` via `ApkInstaller`), `UpdateCheckWorker` (periodic check and notification), and `UpdateStore`. The UI is the `SettingsPage.UPDATES` screen and `WhatsNewSheet`. The server address and version come from Gradle properties `daybreak.updateApiUrl`, `daybreak.versionName`, and `daybreak.versionCode`; without `updateApiUrl` the Updates row is hidden. The version code is `major*10000 + minor*100 + patch` in both the workflow and the server, so minor and patch must stay below 100.

**Minimum version and messages** — the same server answers `GET /v1/status` (`minVersionName`, `minVersionCode`, `messages`), set by hand on its `/admin` page (`ADMIN_TOKEN`). `data/notices/` holds the client: `ServerNoticeRepository.kt` (`ServerNotices` keeps the last answer in `daybreak_notices`, so the minimum also holds offline; the server is asked after the terms are accepted and on every ON_START), `ServerNotices.kt` (pure: parsing, `UpdateGate.isRequired`, `MessageFilter.pending`; unit-tested). `DaybreakApp` has three stages: terms, then `UpdateRequiredRoute` (`ui/update/UpdateRequiredScreen.kt`, the same `UpdateStatusCard` and update flow as the Updates page, Back closes the app) when the installed `versionCode` is below the minimum, then the app. **Debug builds never ask `/v1/status` and ignore a cached answer** (`BuildConfig.SERVER_NOTICES` is false in `debug`, `ServerNotices(enabled = …)`), so the production minimum version cannot block the emulator; opt back in with `-Pdaybreak.debugServerNotices=true`. Updates and the Ko-fi check still use the server. `ServerMessageDialog` shows each pending message once (dismissed ids in the same prefs). The status request sends nothing but the request itself; the legal texts describe it (`LegalTerms.VERSION` 3).

**Settings and theme** — `SettingsRepository` stores plain values in `daybreak_settings` and exposes one `StateFlow<AppSettings>`. `AppSettings.absenceUnit` (Stundenplan settings page) switches the absences page between hours and minutes and school lessons of 50 minutes (`formatSchoolLessons`); the theme hands it to the UI as `LocalAbsenceUnit`. Complex values (lesson colours) are stored as JSON with Gson. `ui/theme/Theme.kt` builds the colour scheme (Material You or one of five accent palettes), and provides composition locals: `LocalSubjectColorMode`, `LocalLessonColors`, and the font scale from `TextScale`.

**Haptics** — `data/haptics/` is Android-free except `VibratorHapticOutput`. `HapticEvent` lists every effect (each is played from some screen; add a call site when you add an event), grouped in `HapticCategory`. `HapticPlanner` turns an event plus `HapticSettings` into `HapticStep`s (primitive, scale, delay): the design of each effect lives in `HapticPlanner.design`; strength is `intensity × category × event × texture`, pulses under 0.05 are dropped, `spacing` stretches the pauses. `Haptics` is the one entry point (`AppContainer.haptics`, provided to Compose as `LocalHaptics`): `perform` honours the master switch, disabled categories/events, the phone's touch-feedback setting (`followSystem`) and the repeat limit (`minGapMs`, only for the throttled categories NAVIGATION/TOUCH/CONTROLS); `preview` ignores all of those so sliders and play buttons can be felt. `VibratorHapticOutput` plays `VibrationEffect.Composition` primitives on Android 11+ (a missing one is swapped for its nearest neighbour), else an amplitude waveform, else a length-only waveform. Settings are `AppSettings.haptics`, stored as JSON by `HapticSettingsCodec` (every field tolerant of missing or unknown values); the screen is `SettingsPage.HAPTICS` (`ui/settings/HapticsScreen.kt`). Edit through `SettingsViewModel.editHaptics`, which re-derives the preset name (`HapticSettings.normalized`: the preset it equals, else CUSTOM). Screens use `HapticSlider` (detent per notch) and `HapticPullToRefreshBox` (tick at the threshold) instead of the plain Material ones. `VIBRATE` is a normal permission and nothing leaves the device, so the legal texts are unchanged.

**Support (Ko-fi)** — `SupportLinks.KOFI_URL` is the donation page; it opens in the browser, the app sends nothing, so the legal texts are unchanged. More → Other has a "Daybreak unterstützen" row (`openSupportPage`). `LoggedInContent` also shows `SupportSheet` rarely: `SupportPromptPolicy` (pure, tested) allows it after 7 different days of use and 7 days since first start, 30 days apart for as long as nothing was paid (no cap), never after a confirmed payment, and never together with the update notes. More → the Ko-fi button also has a "Diesen Button ausblenden" link that opens `HideSupportButtonSheet` (same unlock code and payment check as the popup); the button disappears once `SupportStore.paid` turns true. `SupportStore` keeps the counters in `daybreak_support` (plain numbers, separate from the session). What a timetable client needs stays free; a few **supporter extras** unlock once `SupportStore.paid` is true (More → "Extras für Unterstützer", `SupporterExtras` in `SettingsScreen.kt`: a tinted, starred card with a NEW badge when unlocked; before payment the same rows show dimmed with a lock and open the support sheet, and the card is hidden in builds without an update server since they could never unlock). The first extra is the app name (`data/branding/`, `SettingsPage.APP_NAME`): `AppNamePreset` lists the names under the app icon, each an `activity-alias` of `MainActivity` in the manifest (the only launcher entries; exactly one is enabled; label `launcher_name_*`, kept equal to `displayName` by `AppNameTest`), switched by `LauncherNameSwitcher` (also re-applied in `AppContainer.start()`, so without a payment it falls back to "Daybreak"); `AppSettings.customAppName` is free text that only changes the title on the timetable screen (`LocalAppTitle`, resolved by `AppNaming.resolve`). Android cannot set a free-text launcher name at runtime, which is why the phone name is a preset. The second extra is the app icon (`SettingsPage.APP_ICON`, `AppIconStyle`): STANDARD is the current logo (`ic_launcher_*` drawables, `mipmap-anydpi/ic_launcher*.xml`, with a separate `ic_launcher_monochrome` for themed icons) CLASSIC the original one, and GRID, NIGHT, LETTER and BLOOM separate designs (each style `X` has `ic_launcher_x_background/foreground/monochrome` drawables and `mipmap-anydpi/ic_launcher_x[_round].xml`; keep launcher art inside the 66dp safe circle, tiles in the corners get cut by the round mask); there is one alias per name and style (`Alias<Name>` for Standard, `Alias<Name><Style>` for the rest, 42 in all), so `LauncherNameSwitcher.apply(preset, style)` handles both and `AppNaming.effectiveIconStyle` falls back to STANDARD without a payment. Both pages show `RestartDialog` (`AppRestart.kt`) after switching. Adding a name means an enum entry, a label string and one manifest block per style; adding a style means an enum entry, its art, strings on the icon page and one block per name (the manifest aliases were generated by a script, and `AppNameTest` checks every combination). If the popup is ever made more aggressive or more features are put behind payment, revisit the privacy and terms texts (`legal_terms_body` still says the app is free). **Paid hide:** the popup's "Hide this popup" button is only hidden for good by a confirmed Ko-fi payment. `SupportStore.unlockCode()` makes a random `DB-XXXX-XXXX` code (`SupportCode`, alphabet without 0/1/I/L/O); the supporter pastes it into the Ko-fi message; Ko-fi's webhook (`POST /v1/kofi` on `update-server`, needs `KOFI_VERIFICATION_TOKEN` and a persistent `DATA_DIR`) records it in `support-payments.json`; the app asks `SupportApi.check` (`GET /v1/support/status`) and then `SupportStore.markPaid()` stops the popup. Visiting Ko-fi alone no longer opts out. Without `daybreak.updateApiUrl` (`AppContainer.supportApi == null`) the popup keeps the free "Nicht mehr fragen". The unlock code is sent to the update server, which the legal texts say (`LegalTerms.VERSION` 2 and later); the server stores only code, amount, currency, time and transaction id. The client cannot be made tamper-proof: the check is server-confirmed, but the stored `paid` flag lives on the phone.

**Counted absence time** — teachers often record a whole day as 07:55 to 17:30. The list still shows the recorded range, but the time that counts (card, totals, filter chips) is `UntisAbsence.countedDuration(windows)` (`shared/.../ui/absences/AbsenceCountedTime.kt`): per day, clipped to the first start and last end of the held (not cancelled) lessons. A day inside a loaded week without lessons counts 0; a week that is not loaded keeps the recorded time. `AbsenceLessonHistory.lessonsOfWeeks` fetches only the weeks that hold absences (past weeks are stored once). Lesson-based category counts are unchanged.

**Blocked views** — `UntisPermissionException` (code -8509/-7004, "no right"/"not allowed" messages, REST 403) means the school switched a view off for students (teacher/room timetables, messages). It is not a sign-in failure: Android `toUserMessage` and desktop `Throwable.userMessage` (`ErrorMessages.kt`) say so. Cancellation must never be stored as a load error (`TimetableRepository` rethrows it; this was the desktop "coroutine scope left the composition" message).

**Restart after name/icon switch (Android)** — the launcher alias is no longer switched while the app is open. `RestartActivity` runs in its own process (`:restart`), the main process exits, the alias is switched there and the app is started again (`DaybreakApplication` skips start-up in that process). `AppContainer.start()` still applies the stored name on every start.

**Calendar export (supporter extra, both apps)** — `IcsExport` (shared, pure, unit-tested) builds an .ics (UTC times, cancelled lessons skipped, double lessons merged, exams). Android: `SettingsPage.CALENDAR_EXPORT` shares/opens the file through the FileProvider; desktop: `CalendarExportPage` saves it.

**Desktop shell and support** — `NavHistory` (back/forward; Escape, Alt+Left/Right, mouse side buttons, rail arrows), `SideRail`, tab transitions in `Main.kt`. The desktop has the same Ko-fi flow as Android: `DesktopSupportStore` (paid, unlock code), `DesktopSupportApi` (`/v1/support/status`, parser shared as `PaymentStatusParser`), `SupportDialog`/`HideSupportButtonDialog`, `SupporterExtras` (app name = title in the app and the window title bar, calendar export). The desktop terms are versioned on their own (`LEGAL_VERSION` 6): the desktop now has supporter extras.

**Everyday features (free)** — pure logic lives in `data/schedule/` and `data/reminders/` (Android-free, unit-tested), the UI and jobs call it. *Now and next*: `NowAndNext.compute(lessons, now)` gives the `DayStatus` (current block with minutes left, next block, school end, free period of 30+ minutes, double lessons merged, cancelled lessons skipped); `NowNextCard` sits at the top of today's day view and is switched by `AppSettings.showNowNext`. *Search*: `LessonSearch` over the cached weeks (every word must match subject, teacher, room, class, exam name; upcoming first), shown by `LessonSearchSheet`; tapping a hit jumps to its day. *Share*: `ShareText` formats days (pure), `ShareTimetable` shares them as text or as a picture it draws with Canvas into `cache/shared/timetable.png` (FileProvider path `shared`). *Shortcuts*: static `res/xml/shortcuts.xml` (Today, Week, Search) must be referenced by **every** launcher alias in the manifest (a `<meta-data android:name="android.app.shortcuts">` in each of the 42), because only the enabled alias counts; `MainActivity` reads the `SHORTCUT` extra and passes `startMode`/`openSearch` down to `TimetableScreen`. *Reminders*: `ReminderScheduler` plans two kinds of one-time WorkManager jobs, a summary `leadMinutes` before the first lesson (`MorningSummaryWorker`, planned by `ReminderPlanner.nextMorning` from the cached week, 05:00 at the earliest, skipped on days without school) and a note at 18:00 for exams and homework due the next day (`EveningReminderWorker`). Each job plans its successor; the app, every sync and every settings change plan again, with unique work names per day and `KEEP`, so a missed run heals. `ReminderStore` remembers the last handled day per kind so nothing is announced twice (the day is marked even if nothing was sent, which prevents a retry loop when notifications are refused). `ReminderNotificationManager` builds the texts and has two channels (`daily_summary`, `due_reminders`); the Notifications page has switches, the lead time (30/60/90) and "send a test notification" rows that use real data when there is some. Nothing leaves the device, so the legal texts are unchanged.

**Lesson rendering** — `ui/timetable/TimetableScreen.kt` is the largest file. It holds the day and week pagers, the overlap layout (`layoutTimeline`), the day and week grids, and `LessonDetailsSheet`. Block colours come from `rememberLessonLook` and `rememberSubjectTone` (`ui/components/DaybreakComponents.kt`), with the OKLCH maths in `SubjectPalette.kt`. `examFor` matches an exam to a lesson by date, overlapping time, and subject when the exam has one. The room, teacher and class in `LessonDetailsSheet` are pills (`NameRow`) that look the name up in the master data and, when found, switch the timetable to that element (`TimetableViewModel.setTarget`). A holiday block opens `HolidaySheet`. At most two lessons are drawn side by side (`ui/timetable/TimelineLayout.kt`, `MAX_VISIBLE_COLUMNS`): when more run at once, exams, substitutions and cancelled lessons are kept first (`blockPriority`), and each run of lessons left out gets a "+N" chip (`OverflowChips`) that opens `OverflowSheet`, a list of everything running then; tapping a row opens its details. `LessonDetailsSheet` has a single sheet anchor (`skipPartiallyExpanded`) and scrolls its content; do not animate the size of anything inside it, the sheet sizes itself to its content and it jumped.

## Conventions and gotchas

- Material 3 is pinned to `1.5.0-alpha17` (`gradle/libs.versions.toml`). Expressive APIs need `@OptIn(ExperimentalMaterial3ExpressiveApi::class)`, and `ExperimentalMaterial3Api` for others. `MaterialTheme.motionScheme` specs are springs. For fixed-duration motion, use `tween` with an explicit easing.
- Source files in the working copy have CRLF line endings. Git stores them with LF, so warnings about line endings are expected.
- Android Studio "Run" fails with "Activity class {…/…AliasDaybreak} does not exist" once a supporter name other than "Daybreak" was picked: the launcher entries are `activity-alias`es and only one is enabled, but the default Run launches `AliasDaybreak`. In the Run configuration set Launch Options → Launch: "Specified Activity" → `com.bdersolutions.daybreak.MainActivity` (or `adb shell am start -n com.bdersolutions.daybreak/.MainActivity`). `adb shell pm enable` cannot switch the aliases (only the app itself may).
- After reinstalling the debug build, the app language may revert to German. Check Settings → Language.
- Lint is not clean (see Commands). Fix new lint errors rather than adding to the baseline.
- `README.md` describes the WebUntis login options (QR, manual, password) and the privacy model; it is the reference for those.
